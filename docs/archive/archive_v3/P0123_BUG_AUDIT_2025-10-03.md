### P2 (Medium)
1. **FA sweep lower bound masks high–FA calibration**  
   - **Location:** `src/brain_brr/eval/helpers/false_alarm.py:68-112`  
   - **Issue:** The binary search for `tau_on` clamps the search interval to `[0.1, 1.0]`. When timeline probabilities live below 0.1 (e.g., cold-start models or smoke tests), the search cannot explore the actual operating point required to hit high FA targets. The routine converges to ≈0.1, yields zero predicted events, and reports sensitivity `0.0` even when the requested FA target is unattainable.  
   - **Repro:**
     ```bash
     .venv/bin/python - <<'PY'
     import torch
     from src.brain_brr.eval.helpers.false_alarm import find_threshold_for_fa_target
     from src.brain_brr.config.schemas import PostprocessingConfig

     probs = [torch.full((2560,), 0.09)]   # all logits below 0.1
     labels = [torch.zeros(2560)]
     total_hours = len(probs[0]) / 256 / 3600
     cfg = PostprocessingConfig()

     result = find_threshold_for_fa_target(probs, labels, 10.0, total_hours, [], cfg, 256)
     print(result)
     PY
     ```
     → `FASweepResult(... threshold_tau_on=0.1008789, sensitivity=0.0)`  
   - **Impact:** Evaluation reports that the 10 FA/24h operating point exists, but the returned threshold produces zero detections. This skews TAES comparisons and makes sensitivity-at-FA tables unreliable for under-confident models.  
   - **Recommendation:** Expand the search interval (e.g., start at `low = 0.0` or derive bounds from observed probabilities) and short-circuit with an explicit “target unreachable” flag when the FA curve never crosses the requested rate.

### P3 (Low)
1. **Postprocessing config mutated during CSV export**  
   - **Location:** `src/brain_brr/cli/services/evaluation.py:207-215`  
   - **Issue:** `_export_events_csv_bi` assigns `cfg_for_export = cfg.postprocessing` and mutates `tau_on/tau_off` in place. Subsequent reuse of the same `Config` instance inside a long-running process inherits the evaluation threshold rather than the value persisted in the checkpoint.  
   - **Impact:** Low—current CLI invocations are short-lived, but service integration (or back-to-back evaluations inside a worker) will observe drifted hysteresis parameters.  
   - **Recommendation:** operate on a deepcopy of `cfg.postprocessing` before mutation.

2. **Timeline stitching silently drops mismatched metadata**  
   - **Location:** `src/brain_brr/eval/helpers/timeline.py:34-50`  
   - **Issue:** `zip(file_ids, window_starts, strict=False)` suppresses `ValueError` on length mismatches. If either list is truncated (e.g., partial dataloader replay), windows are silently ignored, leading to incomplete timelines and biased metrics.  
   - **Impact:** Low—datasets currently generate aligned metadata, but enabling `strict=True` would fail fast instead of delivering under-counted recordings.  
   - **Recommendation:** switch to `strict=True` (Py3.11+) or add manual length checks before zipping.

## Suggested Next Steps
1. Patch the FA sweep bounds and add a regression unit test that asserts non-zero events are produced when the FA target is achievable only below 0.1.
2. Wrap CSV export mutations in a config copy to avoid state bleed, and add a smoke test covering repeated `run_evaluation` calls.
3. Harden timeline assembly with strict zipping (plus property-based test using shuffled metadata).

_No other P0/P1 regressions were discovered; overall refactor health remains intact._
